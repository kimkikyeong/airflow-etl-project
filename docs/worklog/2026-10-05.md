## 3. 작업 절차

### Step 1. 원천 데이터 백업

Oracle에서 사용자가 만든 객체는 `TB_LOAN_TRANSACTION`, `DM_LOAN_TRANSACTION_SUMMARY` 두 테이블뿐이었습니다. 마트는 DAG로 재생성할 수 있으므로 **원천만 백업**했습니다.

- `sql/ddl/tb_loan_transaction.sql`: 현재 DB 구조를 그대로 옮긴 원천 DDL
- `backup/export_source.sql`: 원천 데이터를 INSERT 문으로 추출하는 SQL*Plus 스크립트
- `backup/restore_source.sql`: 추출 결과 (INSERT 10건 + `COMMIT`)

```powershell
docker cp backup/export_source.sql oracle-db:/tmp/
docker exec oracle-db sqlplus -s "system/<ORACLE_PWD>@FREEPDB1" "@/tmp/export_source.sql"
docker cp oracle-db:/tmp/restore_source.sql backup/
```

### Step 2. `docker-compose.yml` 수정

| 위치 | 변경 내용 |
|---|---|
| `oracle-db.volumes` | `- oracle_data:/opt/oracle/oradata` 추가 |
| `postgres.volumes` | `- postgres_data:/var/lib/postgresql/data` 추가 |
| 최상위 `volumes` | `oracle_data:`, `postgres_data:` 선언 추가 |
| `airflow-webserver.environment`, `airflow-scheduler.environment` | `- AIRFLOW_CONN_ORACLE_DEFAULT=${AIRFLOW_CONN_ORACLE_DEFAULT}` 추가 |

함께 `.env`를 새로 만들어 `AIRFLOW_CONN_ORACLE_DEFAULT`(JSON 형식, `extra.service_name = FREEPDB1`)를 정의했습니다.

### Step 3. 재기동과 메타데이터 이관

```powershell
docker compose down                       # -v 사용 금지
docker compose create                     # 컨테이너·Named Volume 생성만 (기동 X)
docker run --rm -v <기존 익명 볼륨>:/from -v welcome-project_postgres_data:/to alpine sh -c "cp -a /from/. /to/"
docker compose up -d
docker logs -f oracle-db                  # "DATABASE IS READY TO USE!" 대기
```

- `docker compose create`로 Postgres가 기동하기 전에 빈 Named Volume을 만들고 기존 데이터를 복사했습니다. 이렇게 해서 Postgres가 새 클러스터를 초기화하지 않았습니다.
- 복사 결과 검증: 원본과 대상 모두 50.6M, 소유자 UID 999, `PG_VERSION` 13으로 일치했습니다.
- Oracle은 빈 볼륨이 붙었으므로 DB를 새로 생성했습니다(수 분 소요).

### Step 4. 원천 데이터 복구 및 마트 재생성

```powershell
docker cp sql/ddl/tb_loan_transaction.sql oracle-db:/tmp/
docker cp backup/restore_source.sql oracle-db:/tmp/
docker exec oracle-db sqlplus -s "system/<ORACLE_PWD>@FREEPDB1" "@/tmp/tb_loan_transaction.sql"
docker exec oracle-db sqlplus -s "system/<ORACLE_PWD>@FREEPDB1" "@/tmp/restore_source.sql"
```

이후 Airflow UI에서 `loan_transaction_summary_dag`를 수동 실행해 마트를 재생성했습니다(17:00 KST, success).

### Step 5. 영속성 검증

`docker compose down` → `docker compose up -d` 후 아래 항목을 확인했습니다.

| 확인 항목 | 결과 |
|---|---|
| Oracle 원천 / 마트 건수 | 10 / 10 (재기동 전과 동일) |
| `TX_SEQ` 범위 | 1 ~ 10 (복구 시 재채번) |
| Airflow 기존 계정 로그인 | 성공 |
| DAG 실행 이력 | 전환 전 3건 + 전환 후 1건, 모두 유지 |
| `oracle_default` 해석 값 | `host=oracle-db, port=1521, login=SYSTEM, schema=None, extra={'service_name': 'FREEPDB1'}` → `.env` 값 적용 확인 |
| 볼륨 연결 | `oracle-db` → `welcome-project_oracle_data`, `airflow-postgres` → `welcome-project_postgres_data` |

### Step 6. 미사용 익명 볼륨 정리

검증 완료 후 어떤 컨테이너에도 연결되지 않은 익명 볼륨 7개(모두 과거 Postgres 메타데이터, 47~51MB)를 ID로 지정해 삭제했습니다. 이제 `docker volume ls`에는 Named Volume 2개만 남아 있습니다.

## 4. 트러블슈팅 기록

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | `sqlplus` 실행 시 출력이 전혀 없고, 다음 `docker cp`에서 파일 없음 에러 | 에디터에서 SQL 파일을 저장하지 않아 0바이트 파일이 컨테이너에 복사됨 | 저장(Ctrl+S) 후 `docker cp`부터 다시 실행. 자동 저장(File → Auto Save) 활성화 권장 |
| 2 | `ORA-00904: "TO_CAHR": invalid identifier` | 추출 스크립트 오타 | `TO_CHAR`로 수정. 같은 파일에서 `CUSTID` → `CUST_ID` 오타와 `PRODUCT_CODE`·`TX_TYPE` 사이 구분자 누락도 함께 수정. 구분자 누락은 에러 없이 통과하지만 복구 시 INSERT가 실패하는 백업을 만들기 때문에 미리 잡아야 했음 |
| 3 | `service "oracle-db" refers to undefined volume oracle_data` | 서비스 쪽은 `oracle_data`(언더스코어), 최상위 선언은 `oracle-data`(하이픈)로 이름 불일치 | 양쪽을 `oracle_data`로 통일. `docker compose config --volumes`로 문법 사전 확인 |
| 4 | `the attribute version is obsolete` 경고 | Compose v2는 `version` 속성을 사용하지 않음 | 동작 영향 없음. 1번째 줄 삭제 시 해소 (미조치) |

**PowerShell 사용 시 참고**
- `@`는 PowerShell 특수문자이므로 sqlplus 스크립트 인자는 `"@/tmp/파일.sql"`처럼 따옴표로 감싸야 합니다.
- PowerShell 5.1은 `<` 입력 리다이렉션을 지원하지 않습니다. 그래서 SQL 파일을 `docker cp`로 컨테이너에 넣은 뒤 실행하는 방식을 사용했습니다.

**검증 중 발생한 사고: MERGE 1회 실제 실행**

- **경위**: 렌더링된 MERGE를 `EXPLAIN PLAN FOR`로만 검증하려 했습니다. 그런데 SQL이 빈 줄로 시작해 SQL*Plus가 거기서 문장 입력을 끝냈고(`SQLBLANKLINES OFF` 기본값), MERGE 본문이 단독으로 실행됐습니다. 이어서 SQL*Plus 종료 시 기본 동작(`EXITCOMMIT ON`)으로 커밋됐습니다.
- **영향**: `SUMMARY_DATE = '20261004'` 4건의 `LOAD_TIME`이 17:37 KST로 갱신됐습니다. 원천을 다시 집계한 값과 DM 전체를 비교한 결과 불일치 0건으로, 집계 값 변화는 없습니다(DAG 1회 재실행과 같은 상태).
- **재발 방지**: SQL*Plus로 렌더링된 SQL을 검증할 때는 `SET SQLBLANKLINES ON EXITCOMMIT OFF AUTOCOMMIT OFF`를 지정하고 마지막에 `ROLLBACK`을 넣습니다. 이 설정으로 다시 실행한 결과 데이터 변경이 없음을 확인했습니다.

**문서 반영**: ARCHITECTURE.md의 1.2(전체 흐름), 3.4(타임존 설정), 4장 전체(DAG 속성, 배치 기준일자, Task 의존성, Sensor 설정, 적재 방식 한계), 6.3(템플릿 날짜 변수 주의), 6.4(적용 현황, 남은 고도화)를 갱신했습니다.

### 7.3 비밀 정보 분리 및 Git 저장소 준비

**push 전 점검에서 발견한 문제**

| 파일 | 문제 | 조치 |
|---|---|---|
| `docker-compose.yml` | `ORACLE_PWD`, `POSTGRES_PASSWORD`, `FERNET_KEY`가 평문으로 들어 있음 | 값을 `.env`로 옮기고 `${VAR:?메시지}`로 참조. 값이 없으면 compose가 기동을 거부함 |

| `.claude/settings.json`, `.claude/settings.local.json` | Claude Code 권한 규칙에 비밀번호가 포함된 명령과 로컬 임시 경로가 쌓여 있음 | `.gitignore`로 제외 (`.claude/CLAUDE.md`는 프로젝트 지침이므로 커밋) |
| `logs/`, `dags/__pycache__/` | 런타임 산출물 | `.gitignore`로 제외 |
| `backup/restore_source.sql` | 원천 데이터 | `.gitignore`로 제외 (추출 스크립트 `export_source.sql`만 관리) |

**검증**
- 수정 전후 `docker compose config` 출력이 바이트 단위로 같습니다. 컨테이너에 주입되는 값이 바뀌지 않았으므로 기존 DB와 암호화된 데이터에 영향이 없습니다.
- `docker-compose.yml`에 비밀 값 리터럴이 남아 있지 않음을 확인했습니다.
- 작업 시점에 컨테이너는 사용자가 이미 내려 둔 상태였고(Named Volume 2개는 유지), 별도로 기동하지 않았습니다.

**`requirements.txt`를 만들지 않은 이유**: 현재 추가 의존성은 `apache-airflow-providers-oracle` 하나입니다. 이 의존성은 `docker-compose.yml`의 `_PIP_ADDITIONAL_REQUIREMENTS`에 Airflow 2.8.1 constraints와 함께 명시되어 있습니다. `requirements.txt`를 따로 두면 실제로는 사용되지 않는 두 번째 의존성 목록이 생겨 서로 어긋날 위험이 있습니다. 커스텀 이미지(Dockerfile)로 전환할 때 `requirements.txt`로 분리하는 것으로 정했습니다(ARCHITECTURE.md 6.4).
